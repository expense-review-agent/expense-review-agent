## MODIFIED Requirements

### Requirement: 規範列表

API SHALL 列出啟用中的費用規範，並可選擇依費用類別篩選。每條規範的識別碼 MUST 與案件詳情
檢查所引用的規則代碼一致。

回應 SHALL 涵蓋 Agent **當前會評估的全部檢查**，分兩類且 MUST 可由回應本身區分：

- **組織條文型**：由組織設定的規範。MUST 帶出條文參照與條文原文（原樣保存的組織內容）。
- **產品內建型**：產品內建的安全邊界檢查。這類檢查**沒有對應的組織條文**，因此 MUST 被
  一併回傳而非因缺少條文被排除——它們確實會被評估，漏掉它們會讓呼叫端誤判 Agent 的
  檢查範圍。這類項目的條文參照與條文原文 MUST 為無值，API MUST NOT 以系統文案填補成條文。

每個項目 MUST 帶出該規則是否**只能標示疑似**，以及是否為**產品內建**。這兩個標記 MUST
取自產品擁有的規則型錄，MUST NOT 取自組織可編輯的欄位，也 MUST NOT 由條文原文的字面推斷。
「只能標示疑似」是產品層 guardrail，組織設定 MUST NOT 覆寫它——組織改寫條文原文的字句
MUST NOT 改變該標記的值。

規則名稱與說明 MUST 以訊息識別碼（i18n key）回傳，MUST NOT 回傳已本地化的文字，
顯示文案由呼叫端依識別碼取得。組織設定的條文原文則相反：MUST 原樣回傳，MUST NOT 被
識別碼化。

存在於規則型錄、但組織未設定條文且非產品內建的規則 MUST NOT 出現在回應中——它們不會被
評估，列出它們會讓呼叫端誤以為那些檢查正在生效。

#### Scenario: 列出規範

- **WHEN** 用戶端請求規範列表
- **THEN** 回傳啟用中的規範，各含其規則代碼、條文參照與條文原文

#### Scenario: 規範代碼與案件檢查一致

- **WHEN** 案件詳情的某檢查引用了某規則代碼
- **THEN** 規範列表中存在具相同代碼的規範

#### Scenario: 項目帶出疑似與內建標記

- **WHEN** 用戶端請求規範列表
- **THEN** 每個項目都帶有「是否只能標示疑似」與「是否為產品內建」兩個標記

#### Scenario: 疑似標記取自規則型錄

- **WHEN** 某條只能標示疑似的規範，其組織條文原文的字句未包含「疑似」
- **THEN** 該項目的疑似標記仍為真

#### Scenario: 回應含沒有條文的內建檢查

- **WHEN** 某個產品內建的安全邊界檢查沒有對應的組織條文，且案件檢查會評估它
- **THEN** 回應包含該檢查，其內建標記為真，條文參照與條文原文為無值

#### Scenario: 未設定的規則不在回應中

- **WHEN** 規則型錄中某規則沒有對應的組織條文，也不是產品內建檢查
- **THEN** 回應不含該規則

#### Scenario: 名稱以訊息識別碼回傳

- **WHEN** 用戶端請求規範列表
- **THEN** 每個項目的名稱欄位為訊息識別碼而非已本地化的文字，而條文原文欄位為組織填寫的原文
