# Review Case（案件初審分析）

> 依 `docs/product/prd-review-criteria.md` 之 Feature Spec 階段規則撰寫：逐項套用四大類別，不適用項目標示 N/A 並說明原因。

## User Story

As a CheckMate Agent（代表財務／會計初審人員執行初審）
I want 針對一筆已標準化的費用案件，自動完成必要檢查、辨識關鍵問題，並產生一致的審查建議
So that 財務人員可以快速判斷這筆案件是否可以繼續處理、需要補件，或需要人工審核，而不必逐筆手動比對

## Context

本 Spec 對應 `docs/product/user-flow.md` 全局流程中「擷取與整理資料 → 比對佐證資料 → 套用企業規範／法規／風險判斷 → 產生發現項目 → 產生審查建議」這一段，也就是 CheckMate 的第一個核心使用情境：**案件初審分析**。

本次 Slice 範圍：
- 輸入為一筆**已標準化**的模擬費用案件（含申請資料與佐證資料），資料上傳、OCR、真實系統串接不在此範圍。
- 只做到「產生審查建議並留下可追溯紀錄」為止；REQUEST_INFO／ESCALATE／PROCEED／OVERRIDE 等流程動作與人工介面操作，屬於後續 Slice，本次不展開。
- 台灣法規遵循（Taiwan Compliance）本次不涵蓋（見下方 N/A 說明），僅涵蓋佐證比對、企業規範審查、風險訊號三類必要檢核。

## Behavior

### 分析流程

```text
輸入：一筆標準化模擬案件（申請資料＋佐證資料）
  → 佐證比對（Evidence Matching）
  → 企業規範審查（Corporate Policy Review）
  → 風險訊號檢查（Risk Signals）
  → 產生發現項目（Finding），每筆包含：
       - 來源（Evidence Match／Corporate Policy／Risk Signal）
       - 嚴重程度（Blocking／Needs Attention／Informational）
       - 對審查建議的影響（RequiresReview／RequiresInfo／None）
       - 說明文字與對應規則／佐證參照
  → 依下列規則推導審查建議（Recommendation）
  → 產生一筆審查紀錄（Review Record），附加至案件的審查歷程（不覆蓋既有紀錄）
```

### 審查建議推導規則（優先序由上到下）

1. 只要存在任一「需人工審核」類發現項目（違規、風險訊號、資料衝突、需專業判斷）→ **建議人工審核**
2. 否則，只要存在任一「可補正缺漏」類發現項目（缺少必要佐證／欄位）→ **建議補件**
3. 否則 → **建議通過**（允許同時存在 Needs Attention／Informational 的發現項目）

此規則同時滿足：資訊不足且可補正 → 建議補件；資料完整但有風險／需判斷 → 建議人工審核；必要檢核全部通過 → 建議通過。

### 必要檢核（Required Checks，本次 Slice）

- **佐證比對（Evidence Matching）**：申請金額與佐證金額是否一致；必要佐證是否齊全。
- **企業規範審查（Corporate Policy Review）**：套用 5–8 條模擬規範（金額上限、必要附件、可報支類別、申報期限）。
- **風險訊號（Risk Signals）**：本次只實作「疑似重複申報」（同一申請人、相近金額、相近日期與供應商，比對既有模擬案件）。

### 可追溯原則（本次 Slice 的落地方式）

- 每次執行分析都會產生一筆新的審查紀錄，附加到案件的審查歷程陣列，不修改或刪除先前紀錄。
- 案件目前的審查建議，對應審查歷程中最新一筆紀錄。

## Acceptance Criteria

- Given 一筆案件資料完整、金額與佐證一致、無政策違規、無風險訊號
  When 執行分析
  Then 產生審查建議「建議通過」，且不含任何「需人工審核」或「可補正缺漏」類發現項目

- Given 一筆案件缺少企業規範要求的必要佐證（例如缺少發票）
  When 執行分析
  Then 產生一筆「可補正缺漏」類發現項目，說明缺少的項目，審查建議為「建議補件」

- Given 一筆案件的申請金額與佐證金額不一致
  When 執行分析
  Then 產生一筆「需人工審核」類發現項目（金額不一致可能為誤植或風險，不視為單純可補正缺漏），審查建議為「建議人工審核」

- Given 一筆案件的申請金額超出對應類別的企業規範金額上限
  When 執行分析
  Then 產生一筆企業規範違規的「需人工審核」類發現項目，審查建議為「建議人工審核」

- Given 一筆案件與既有模擬案件在供應商、金額、日期上高度相近（疑似重複申報）
  When 執行分析
  Then 產生一筆風險訊號的「需人工審核」類發現項目，審查建議為「建議人工審核」

- Given 同一筆案件被重複執行分析兩次
  When 第二次執行完成
  Then 案件的審查歷程包含兩筆紀錄，第一筆紀錄的內容未被覆蓋或修改

## Edge Cases

- 同時存在「可補正缺漏」與「需人工審核」類發現項目 → 依優先序，最終審查建議為「建議人工審核」（人工審核優先於補件）。
- 案件沒有任何發現項目 → 建議通過。
- 案件完全沒有附上任何佐證資料（不是「金額不符」而是「完全缺失」）→ 視為缺少必要佐證，「可補正缺漏」類發現項目，若無其他需人工審核情況則建議補件。

## PRD Review Criteria 檢查（Feature Spec 階段）

### 1. 流程完整性
- 涵蓋主要使用流程：Acceptance Criteria 第一項（正常案件）。
- 起始條件：案件資料已標準化並包含申請與佐證資料（本 Spec 假設此前置條件已滿足，資料標準化本身不在此 Spec 範圍）。
- 結束條件：產生審查建議並寫入審查歷程。
- 空白／無資料條件：案件完全無佐證資料時，歸類為「可補正缺漏」（見 Edge Cases）。
