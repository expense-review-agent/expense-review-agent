# PRD Review Criteria

> 本文件為撰寫與檢視 User Story、User Flow、Edge Case、PRD、Feature Spec、Acceptance Criteria 時的共同檢查基準。
>
> 使用原則：
> 1. 撰寫階段就要主動套用，不是完成後才拿來檢查。
> 2. 若某一子項目前因 Demo／Mock Scope 不適用，須在文件中標示「N/A」並說明原因，不可直接省略不提。
> 3. 本文件的目的是避免遺漏，不代表每一份文件都要塞進所有細節；資訊應放在對應的文件層級（例如效能門檻屬於 Spec／Acceptance Criteria 層級，不需要出現在 User Flow）。

## 1. 流程完整性（Process Completeness）

| 子項目 | 說明與示例 |
|---|---|
| 涵蓋主要使用流程（Happy Path） | 正常使用路徑完整，例如：登入 → 查詢資料 → 顯示結果 |
| 描述起始條件／前置條件 | 例如「已登入」、「資料庫中有至少 1 筆記錄」 |
| 描述結束條件／成功條件 | 例如「頁面跳轉至 Dashboard 並顯示成功訊息」 |
| 描述空白條件／無資料條件 | 例如「無資料時的顯示訊息」 |
| 提及跨模組／系統串接與依賴性 | 例如「呼叫支付 API 後更新訂單狀態」，需考慮 API 不可用情境 |

## 2. 細節明確度（Clarity & Specificity）

| 子項目 | 說明與示例 |
|---|---|
| 每步驟輸入、輸出、狀態變化清楚 | 例如「輸入 Email 格式：xxx@domain.com」、「狀態 pending → approved」 |
| UI／API 行為明確 | UI 欄位必填／禁用條件；API 回應碼與 Payload 格式，需考慮行動裝置相容性 |
| 使用可衡量條件 | 例如「回應時間 < 2 秒」、「支援 1000 筆資料分頁」 |
| 資料格式／單位／範圍與國際化 | 例如「日期採 ISO 8601、數字範圍 1–100、支援多語系」 |

## 3. 異常與例外情境（Error & Edge Cases）

| 子項目 | 說明與示例 |
|---|---|
| 描述異常流程 | 例如「失敗可重試 3 次後鎖定」、「逾時 30 秒顯示錯誤」，含網路斷線情境 |
| 定義錯誤訊息與顯示條件 | 例如「當欄位為空時顯示：此欄位為必填」 |
| 考慮邊界案例與安全性 | 例如「輸入最大值」、「快速連續點擊」、「防 SQL Injection」 |

## 4. 測試與驗收（Testability）

| 子項目 | 說明與示例 |
|---|---|
| 每條 Acceptance Criteria 可被明確驗證 | 例如「點擊按鈕後資料儲存成功」，而非「系統運作順暢」 |
| 可由 QA／自動化測試直接套用 | 適合直接寫成自動化腳本驗證 UI 或 API |
| 包含非功能需求 | 例如「支援 IE11+」、「敏感資料加密」、「500 同時使用者無降速」 |

## 使用時機

- 撰寫 User Story、User Flow、Edge Case 時：優先檢查「1. 流程完整性」與「3. 異常與例外情境」是否涵蓋，避免只寫 Happy Path。
- 撰寫 Feature Spec、Acceptance Criteria 時：四大類別皆需檢查，特別是「2. 細節明確度」與「4. 測試與驗收」，確保行為可被實作與驗證。
- 目前 Demo／Mock Scope 下常見的 N/A 情境（例如國際化、跨系統依賴、非功能性效能需求），仍需標示 N/A 並簡述原因，而非略過不提。
