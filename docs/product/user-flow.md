# User Flow（全局產品骨架）

> 本文件定位為 CheckMate 的全局產品骨架，目的是確保核心概念之間不互相衝突，不是完整 Feature Spec。詳細行為規則將於對應的 Product Slice 收斂後補進 specs/。
>
> 文件優先順序仍依 CLAUDE.md：若本文件與 Product Brief／Product Scope 衝突，以 Product Brief／Product Scope 為準，不自行選擇答案。

## 壹、核心角色

- **Agent**：依企業規範與可判斷條件完成案件初審，並在符合自動執行條件時直接完成後續處置。
- **人工（財務／會計初審人員）**：處理 Agent 無法自動完成的案件，可執行對應動作，或於不同意 Agent 判斷時進行決策覆寫（Override）。
- 主管／稽核等角色目前只作為稽核紀錄的查閱者，不參與案件當下的處理流程，暫不在此骨架中展開。

## 貳、基本流程（案件進入 → 初審完成）

```text
案件進入（模擬批次／檔案上傳）
  → 擷取與整理資料
  → 比對申請與佐證資料（Evidence）
  → 套用企業規範／法規／風險判斷
  → 產生發現項目（Finding）
  → 產生審查建議（Recommendation）
  → 若建議通過，且符合自動執行條件 → Agent 自動執行 PROCEED
  → 寫入稽核紀錄
  → 案件初審完成
```

若案件無法滿足「建議通過且符合自動執行條件」（例如證據不足、存在需要人工判斷的風險，或雖建議通過但不符合自動執行條件），案件轉為人工處理：人工於案件詳情檢視相關資訊後，執行對應動作。各種轉人工的具體分支與判斷細節，將在對應情境的 Product Slice 中展開，不在此骨架文件一次定義完成。

## 參、三種對外審查建議

- **建議通過**：必要檢查已完成，且沒有需要人工判斷的風險。不代表最終核准。
- **建議補件**：缺少完成初審所需的資料或證據。
- **建議人工審核**：存在風險、例外或需要專業判斷的情況。

三者為固定的對外結論，不新增第四種或變體用語。

## 肆、Agent 自動處理與人工介入的基本關係

- 審查建議（Recommendation）與「是否能由 Agent 自動執行」是兩層獨立判斷：審查建議回答案件初審結論，自動執行條件只回答這個動作能不能由 Agent 直接完成。
- 「建議通過」不保證一定由 Agent 自動執行；不符合自動執行條件時，改由人工執行。
- Agent 與人工共用同一組工作流程動作（Workflow Action）：PROCEED／REQUEST_INFO／ESCALATE，不新增人工專屬的動作名稱。
- OVERRIDE 屬於人工決策覆寫，不是工作流程動作本身；人工覆寫 Agent 判斷後，仍必須接續執行 PROCEED／REQUEST_INFO／ESCALATE 其中之一。
- 執行者的差異透過稽核紀錄的 Actor（Agent／人工）欄位呈現，而不是呈現成使用者需要另外理解的第二套判斷結果。

## 伍、可追溯原則

- Agent 的每一次判斷、人工的每一次決策與執行動作，皆須留下可追溯紀錄，至少包含時間、執行者（Actor）、動作、結果與原因。
- 案件的審查建議若因重新評估而更新，先前的審查建議需保留於可追溯紀錄中，不能被覆蓋或消失。

## 陸、產品邊界

CheckMate 是費用初審與風險辨識的 Review & Control Layer，本流程只涵蓋到「案件初審完成」或「轉交人工」為止；不涉及最終核准、正式會計入帳、自動付款、正式稅務申報或最終法律判定（詳見 product-brief.md）。

## 柒、Open Questions / Deferred Decisions

以下問題目前不影響「正常案件初審」這條核心流程，暫不強行決策，待對應情境實際開發時再確認：

- 建議通過但無法自動執行的案件，在案件狀態上如何呈現（是否需要新增狀態），待實際開發此流程時與 UX／狀態模型一併決定。
- 人工決策覆寫（OVERRIDE）是否允許被二次覆寫。
- REQUEST_INFO（要求補件）逾期後，是否需要催辦或升級，目前不做任何自動處理。
- 補件完成後重新評估的範圍與案件狀態銜接方式。
- 多筆風險發現（Finding）同時存在時的呈現優先序與分層標示細節。
- 佐證資料不一致（例如申請金額與單據金額不符）應歸類為可補正或需人工判斷。
- 台灣法規檢核無法明確判斷時，發現項目（Finding）標示來源的呈現方式。
- 既有文件（Product Brief／Product Scope／Design System／Interaction Patterns）與本文件用詞風格是否需要統一。
